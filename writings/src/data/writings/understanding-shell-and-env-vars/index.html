How a Shell Works, Processes, System Calls, and Environment Variables

2026-06-09 ·
  •  linux
  •  shell
  •  systems

    • What happens when you type ls and hit Enter? If you can’t confidently answer that right now don’t worry. By the end of this article, you’ll have a clear understanding, and you’ll have built a simple version of a shell yourself.

    What is a Process?

    A running instance of a program. It has its own address space, execution context, and resource state all tracked by the kernel via the Process Control Block (PCB).

    A process has its own:

    • Address space: the memory it can use (stack, heap, data, text/code segments)
    • Execution context: program counter, CPU registers, stack pointer
    • Resource state: open file descriptors, memory mappings, signal handlers

    The operating system tracks all of this using a special kernel data structure called the Process Control Block (PCB).

    Process Address Space

    Every process gets its own virtual address space. Here’s how it’s laid out:

    Peeking into a Process with /proc

    Linux exposes process information through the /proc filesystem. Every process has a directory named after its PID. You can explore the current shell’s process like this:

    # See process status (PID, PPID, state, memory, etc.)
cat /proc/self/status

# See memory mappings (address space layout)
cat /proc/self/maps

# See open file descriptors
ls -l /proc/self/fd/

    System Calls: The Gateway to the Kernel

    A system call (syscall) is the mechanism through which a user-space program requests a service from the kernel.

    Ring 0 vs Ring 3

    The CPU enforces privilege levels, often called rings:

    Ring 0 (Kernel mode): The kernel runs here. It can:

    • Execute privileged CPU instructions
    • Access any memory
    • Manage processes and threads
    • Write directly to disk
    • Modify page tables

    Ring 3 (User mode): Your programs (Chrome, VS Code, ls) run here. They cannot directly:

    • Write to disk
    • Modify page tables
    • Access hardware

    So how does ls read files from disk? It asks the kernel politely through a system call.

    Common System Calls

    SyscallWhat it does
    openatOpen a file (modern variant of open)
    readRead from a file descriptor
    writeWrite to a file descriptor
    forkCreate a copy of the current process
    execveReplace the current process with a new program
    mmapMap memory pages
    waitWait for a child process to finish
    exitTerminate the current process

    The C standard library (libc) wraps these raw syscalls into functions you can call. The header <unistd.h> contains declarations for many of them.

    Seeing Syscalls in Action with strace

    strace is a tool that prints every syscall a program makes. Let’s trace a simple ls:

    strace ls

    You’ll see a flood of openat, read, write, mmap, and close calls all the ingredients that make ls work. To focus on just a few:

    strace -e trace=execve,read,write ls

    Run this and observe. You’ll see execve is how the shell launches ls, and read/write are how data moves around.

    fork(): The Cloning Mechanism

    fork() creates a copy of the current process. The process that calls fork() is called the parent, and the copy is called the child.

    Key Behaviour

    • Parent gets a return value of the child’s PID (a positive number)
    • Child gets a return value of 0
    • Both processes start executing from the very next line after fork()
    • The child is an almost-exact copy same memory, same file descriptors, same program counter
    #include <stdio.h>
#include <unistd.h>

int main() {
    pid_t pid = fork();

    if (pid == 0) {
        printf("Child: this is child with PID = %d\n", getpid());
    } else {
        printf("Parent: this is parent with PID = %d\n", getpid());
        printf("Parent: child's PID = %d\n", pid);
    }

    return 0;
}src/fork-example.c

    Possible Output

    The output order is non-deterministic the scheduler decides whether the parent or child runs first. Here’s one possible output:

    Parent: this is parent with PID = 17416
Parent: child's PID = 17417
Child: this is child with PID = 17417

    But this is equally possible:

    Child: this is child with PID = 17417
Parent: this is parent with PID = 17416
Parent: child's PID = 17417

    Copy-on-Write (COW)

    In reality, fork() doesn’t physically copy all of the parent’s memory immediately that would be extremely slow. Instead, the kernel uses Copy-on-Write: parent and child share the same physical pages. Only when one of them tries to write to a page does the kernel actually duplicate it. This is an optimisation worth reading about. Copy-on-Write on Wikipedia

    Zombie and Orphan Processes

    • Zombie: If the parent doesn’t call wait() to reap the child, the child becomes a zombie it’s terminated but still occupies a slot in the process table. You can spot them with ps aux | grep Z.

    • Orphan: If the parent dies before the child, the child becomes an orphan and is adopted by init (PID 1), which will eventually clean it up.

    Retrieving the Exit Status waitpid

    wait() is simple, but waitpid() gives you more control and access to the child’s exit status:

    #include <sys/wait.h>

int status;
pid_t pid = waitpid(child_pid, &status, 0); // replace child_pid with actual pid

if (WIFEXITED(status)) {
    printf("Child exited with status: %d\n", WEXITSTATUS(status));
}src/waitpid-example.c

    Exploring Fork with /proc

    After a fork, check the parent-child relationship:

    # In the parent, before fork:
echo $$          # parent PID
cat /proc/$$/status | grep -E "^(Pid|PPid):"

    Run this inside the child too (via your C program) and compare the PPID values.

    execve(): The Transformation

    While fork() clones, execve() replaces. It replaces the entire current process code, data, stack, heap with a brand new program loaded from disk.

    Key Behaviour

    • The PID stays the same, the process doesn’t end, it transforms
    • Everything after execve() runs only if execve fails
    • The argv array becomes the new program’s command-line arguments
    • The envp array becomes the new program’s environment variables
    #include <stdio.h>
#include <unistd.h>

int main() {
    char *bin_path = "./print_banana";
    char *argv[] = {
        bin_path,
        NULL
    };
    char *envp[] = {
        NULL
    };

    printf("print before execve\n");
    execve(bin_path, argv, envp);
    printf("print after execve\n");  // This runs ONLY if execve fails
}src/execve-example.c

    Output:

    print before execve
banana

    Notice: “print after execve” never appears, the process was replaced.

    The exec() Family

    execve is the true syscall. The other variants are libc convenience wrappers:

    FunctionProgram specified asArguments passed asEnvironment
    execvePathArray (char *argv[])Explicit array
    execvpFile (searches $PATH)ArrayInherited from parent
    execlpFile (searches $PATH)List (arg0, arg1, ..., NULL)Inherited from parent
    execlePathListExplicit array

    Use execvp when you want automatic $PATH lookup. Use execve when you need full control.

    Environment Variables: Passing Context

    Environment variables are a list of KEY=VALUE strings that a process inherits from its parent and passes to its children. They provide execution context where to find commands, the user’s home directory, preferred language, and more.

    Viewing Environment Variables

    env

env | head -5

    Key variables you’ll see:

    VariablePurpose
    PATHDirectories to search for executables
    HOMECurrent user’s home directory
    USERCurrent username
    SHELLPath to the user’s login shell
    PWDCurrent working directory

    The environ Global Variable

    The execve syscall receives an envp array. In a running C program, this array is accessible through the global variable extern char **environ. You can write your own env command in just a few lines:

    #include <stdio.h>

extern char **environ;

int main() {
    for (char **e = environ; *e != NULL; e++) {
        printf("%s\n", *e);
    }
}src/my-env.c

    Compile and run it, you’ll see the same output as the env command. you can use getenv and setenv to access and modify environment variables programmatically.

    Shell Variables vs Environment Variables

    This is an important distinction:

    # Shell variable (exists ONLY in the current shell)
MY_VAR="hello"

# Environment variable (passed to child processes)
export MY_VAR="hello"

    A variable set without export is a shell variable it lives only in the shell’s own memory. It won’t appear in env and won’t be inherited by programs you run. Adding export promotes it to an environment variable that child processes inherit.

    Environment Variables in the Real World

    Now that you understand the mechanics, here’s how env vars show up in everyday software development.

    Python reads them via os.environ, which is just the environ array we’ve been working with all along:

    import os

db_url = os.environ.get("DATABASE_URL", "sqlite:///default.db")
debug  = os.environ.get("DEBUG", "false").lower() == "true"

    Node.js exposes them through process.env:

    const port = process.env.PORT || 3000;
const apiKey = process.env.API_KEY;  // set by the deployment environment

    Docker injects env vars into containers using the ENV instruction in a Dockerfile or -e flags at runtime:

    ENV NODE_ENV=production
ENV PORT=8080
    docker run -e DATABASE_URL=postgres://... myapp

    CI/CD pipelines (GitHub Actions, GitLab CI, etc.) use env vars to inject secrets at build and deploy time.

    - name: Deploy
  env:
    API_KEY: ${{ secrets.API_KEY }}
  run: ./deploy.sh

    The underlying mechanism is always the same: the parent process (Docker daemon, CI runner, shell) sets up the environment, then fork+execve passes it to the child. You’ve now built the mental model that explains all of these.

    Reading Environment Variables from /proc

    # The environment of the current process (null-separated, so we translate)
cat /proc/self/environ | tr '\0' '\n'

    ⚠️ Security: Don’t Pass Secrets Through Environment Variables

    Since /proc/PID/environ is readable by the same user (and sometimes by others depending on system configuration), environment variables are not a safe place for passwords, API keys, or other secrets. They are visible to anyone who can read /proc, and they also appear in process listings and crash dumps.

    The common pattern developers use instead is a .env file a plain text file in your project root that is never committed to version control:

    # .env  (add this to .gitignore!)
DATABASE_URL=postgres://localhost/mydb
API_KEY=sk-abc123

    Tools like direnv automatically load a .env file into your shell’s environment when you cd into a directory, and unload it when you leave. This gives you the convenience of env vars without the risk of accidentally hardcoding secrets into your shell profile or committing them to git.

    # Install direnv, then in your project directory:
echo "dotenv" >> .envrc
direnv allow
# direnv will now auto-load .env whenever you enter this directory

    Secrets in environment variables

    Use .env files for secrets, use direnv to manage them, and always add .env to your .gitignore.

    Building a Mini Shell: Putting It All Together

    Now we have all the pieces. Here’s how a shell runs your commands:

    The shell:

    1. Reads your input (e.g., ls -la /home)
    2. Tokenizes it into the command name and arguments
    3. Checks if it’s a builtin (like cd, exit) these run inside the shell process
    4. For external commands: searches each directory in PATH for the executable
    5. Once found: forks a child process
    6. The child calls execve with the full path, arguments, and environment
    7. The parent calls wait to wait for the child to finish
    8. The prompt returns and the loop repeats

    Let’s build this in stages.

    Stage 1: Fork + Execve with a Hardcoded Path

    This is the simplest possible “shell” it runs exactly one hardcoded program:

    #include <stdio.h>
#include <unistd.h>
#include <sys/wait.h>

int main() {
    pid_t pid = fork();

    if (pid == 0) {
        char *bin_path = "./own_env";
        char *argv[] = {
            bin_path,
            NULL
        };
        char *envp[] = {
            "HERO=Tom_Cruise",
            "MOVIE=TopGun_Maverick",
            "DIRECTOR=Joseph_Kosinski",
            NULL
        };

        execve(bin_path, argv, envp);
    }

    wait(NULL);
    printf("parent: Child finished\n");

    return 0;
}src/stage1-hardcoded.c

    This demonstrates the fork+execve pattern with custom environment variables, but it only runs one hardcodedprogram. We’ll expand it to search PATH and execute any command. PATH is an environment variable that is a colon-separated list of directories where the shell looks for executables:

    echo "$PATH" | tr ':' '\n'
# /home/pankaj/.local/bin
# /usr/local/bin
# /usr/bin
# /usr/bin/site_perl
# /usr/bin/vendor_perl
# /usr/bin/core_perl

    Stage 2: Simple Shell

    Here’s the simple shell. It:

    • Reads the PATH from the environment
    • Takes your commands as input in an infinite loop
    • Parses the command into arguments
    • Searches each PATH directory for a matching executable
    • Forks and executes it, passing the shell’s environment
    • Waits for the child to finish, then loops
    simple shell code (click to expand) 
    #include <linux/limits.h>
#include <stddef.h>
#include <stdio.h>
#include <unistd.h>
#include <sys/wait.h>
#include <string.h>
#include <dirent.h>
#include <stdbool.h>

extern char** environ;
#define MAX_DIRS 20
#define MAX_DIR_LEN 256
#define MAX_PATH_LEN ((20 * 256) + 19)

void add_char(char* src, int ind, char* dst){
    size_t cur_len = strlen(dst);
    if(cur_len == MAX_DIR_LEN) return;
    dst[cur_len] = src[ind];
    dst[cur_len+1] = '\0';
}

bool search_execute(char* dir, char** argv){
    DIR *folder;
    struct dirent *entry;
    char* target = argv[0];

    folder = opendir(dir);
    if(folder == NULL){
        return false;
    }

    while ((entry = readdir(folder)) != NULL) {
        if(strcmp(entry->d_name, target) == 0){
            char complete_path[MAX_PATH_LEN] = "";
            strcpy(complete_path, dir);
            strcat(complete_path, "/");
            strcat(complete_path, target);

            if (access(complete_path, X_OK) != 0) {
                continue; // Skip if it is not actually executable
            }

            printf("\nyes master i found it, now executing %s\n", complete_path);
            printf("----------------------------------------\n");
            int pid = fork();
            if(pid == 0){
                execve(complete_path, argv, environ);
                perror("something went wrong\n");
                _exit(1);
            }

            wait(NULL);
            printf("----------------------------------------\n");
            printf("execution is done Master\n");
            closedir(folder);
            return true;
        }
    }

    closedir(folder);
    return false;
}

void run_shell(char dirs_to_search[][256]){
    char input_command[1024];
    printf("\nTell me what to run Master: ");

    if (fgets(input_command, sizeof(input_command), stdin) == NULL) {
        return;
    }
    input_command[strcspn(input_command, "\n")] = '\0';

    if(strlen(input_command) == 0) {
        return;
    }

    char* argv[64];
    int argc = 0;
    char* token = strtok(input_command, " ");
    while(token != NULL && argc < 63) {
        argv[argc++] = token;
        token = strtok(NULL, " ");
    }
    argv[argc] = NULL;

    if (strcmp(argv[0], "exit") == 0) {
        return;
    }

    bool found = false;
    for(int i = 0; i < MAX_DIRS; i++){
        if (dirs_to_search[i][0] == '\0') continue;
        found = search_execute(dirs_to_search[i], argv);
        if(found) break;
    }

    if(!found) {
        printf("Command not found\n");
    }
}

int main(){
    // each path with 64 chars and a max of 64 paths
    char path_string[MAX_DIRS * MAX_DIR_LEN] = "";
    for(char **e = environ; *e != NULL; e++){
        if(strncmp(*e, "PATH=", 5) == 0){
            printf("path is: %s\n", *e+5);
            printf("path length: %d\n", (int)strlen(*e)-5);
            if(strlen(*e)-5 > MAX_PATH_LEN){
                printf("path length is too big for this program\n");
                return 0;
            }

            strncpy(path_string, *e+5, sizeof(path_string)-1);
            break;
        }
    }

    char dirs_to_search[MAX_DIRS][MAX_DIR_LEN];
    for(int i=0; i<MAX_DIRS; i++) dirs_to_search[i][0] = '\0'; // Initialize

    size_t dir_ind = 0;
    char temp_string[MAX_DIR_LEN] = "";
    for(size_t i = 0; i < strlen(path_string); i++){
        if(path_string[i] == ':'){
            printf("%s\n", temp_string);
            if (dir_ind < MAX_DIRS) strcpy(dirs_to_search[dir_ind], temp_string);
            temp_string[0] = '\0';
            dir_ind++;
            continue;
        }

        add_char(path_string, i, temp_string);
    }
    printf("%s\n", temp_string);
    if (dir_ind < MAX_DIRS) strcpy(dirs_to_search[dir_ind], temp_string);
    temp_string[0] = '\0';
    dir_ind++;

    while(1){
        run_shell(dirs_to_search);
    }
    return 0;
}src/simple_shell.c

    This shell supports commands like ls, cat, pwd, env, which, make anything in your PATH. Try it!

    Ideas to Extend Your Shell

    • Add piping (|) : redirect stdout of one process to stdin of another using pipe() + dup2()
    • Add redirection (>, <, >>) : redirect stdout/stderr to files or use open() + dup2()
    • Add background execution (&) : skip the wait() call
    • Add signal handling : Ctrl+C (SIGINT) should kill the foreground child, not the shell
    • Add history : store previous commands in a buffer
    • Better argument parsing : handle quoted strings ("hello world" as one argument)

    Process Tree with pstree

    Every process (except init/systemd, PID 1) has a parent. Now that your mini shell is running, you can actually see yourself in the process tree. Run pstree to visualise it:

    pstree -p

    You’ll see your terminal emulator → shell → commands you run, all linked in a parent-child chain. Your simple shell will appear there too.

    Summary

    Here’s the complete picture:

    • Processes: running program instances with their own address space, tracked by PCBs
    • System calls: how user programs request kernel services through the Ring 0/Ring 3 boundary
    • fork(): cloning a process (and why Copy-on-Write makes it efficient)
    • execve(): replacing a process with a new program
    • Environment variables: the key-value context passed from parent to child through fork+exec
    • How a shell works: reading input, searching PATH, forking, and executing

    And you built one yourself. The next time you type ls, you’ll know exactly what happens from keystroke to output.
